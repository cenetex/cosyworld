# Fast deploys

Written against rules 204 (`1198b0235`). Paths are relative to the repository root; `card-game/` means `v2/card-game/` and `rust/` means `v2/orchestrator-rust/src/`. Measurements were taken on 2026-11-25 on a 2-CPU machine (debug builds unless marked).

## Runtime-loaded assets

Today `build.rs` embeds every public card-game file (2,665 files, 956 MB) with generated `include_bytes!`, and the crate embeds 72 frozen rules bundles (36.5 MB), `content.json`, `narrator.js`, `authored-text.json` and `packs.json` with `include_str!`. `build.rs` also watches all of `card-game/`. So every JS, rules, content or art change reruns the build script, rebuilds a 1 GB lib and recompiles the bin (45-51 s in debug, 51-72 s in CI release), and ships a new ~1 GB binary layer. The debug binary is 1.13 GB, of which 998 MB is `.rodata`.

The goal: a change that touches no Rust recompiles no Rust. The server reads those files at startup from an assets directory shipped beside the binary, so a non-Rust deploy can become a file sync plus a restart or reload.

### What moves out of the binary

| Files | Today | After |
|---|---|---|
| The 2,665 public files (`public-assets.mjs`) | `include_bytes!` in a module generated by `build.rs` | `card-game/` in the assets dir, served by the same handler |
| Rules bundles `engine-v133.js` ... `engine-vNNN.js` | `include_str!`, 72 constants and 142 hand-wired match arms and list entries in `engine.rs` and `full_world.rs` | `card_shared/` in the assets dir, listed by `card_shared/rules.json` |
| `content.json`, `narrator.js` | `include_str!` in `content.rs`, `narrator.rs` | `card_shared/` in the assets dir |
| `authored-text.json` | `include_str!` in `authored.rs`, `imported.rs` | `card_narrative/` in the assets dir |
| `packs.json`, `forest.json`, `shared-cast.json`, `voices.json`, `entity-profiles.json`, `boardyai.json`, `emoji-symbols.json` | `include_str!` in 9 production files | already public files: read through the asset store |
| `senses.json`, `radio-catalog.json`, `assets/discord-faces.json` | `include_str!` | `card-game/` in the assets dir, listed but not served |

### Layout and lookup

```
assets/
  manifest.json            one entry per file: sha256, size, and for served files a content type
  card-game/...            the public files, same paths as v2/card-game/
  card_shared/rules.json   version -> sha256 pins for every frozen bundle
  card_shared/engine-vNNN.js, content.json, narrator.js
  card_narrative/authored-text.json
```

The server looks in this order:

1. `COSYWORLD_ASSETS_DIR`, if set. The image sets it to `/app/assets`, so a production server never reaches step 3.
2. `assets/` beside the executable, if it holds `manifest.json` (the desktop app's `game/assets`).
3. The source tree. The server runs `node v2/scripts/build-card-assets.mjs --manifest -` once at startup and reads the files in place. This is the path for `cargo run`, `cargo test` and the smokes that spawn the debug binary, so they always see the working tree and nothing needs regenerating first.

`node v2/scripts/build-card-assets.mjs --release <dir>` writes a release directory: the files and `manifest.json`, split into `<dir>/media` (images and audio) and `<dir>/text` (everything else, with the manifest) so the two can be separate image layers.

`manifest.json` keeps today's `manifest_sha256()` identity, the hash of the `[file, sha256]` list of the public files, so `/meta` `assets_sha256` and the media etags are unchanged.

### Integrity

- At startup the server reads `manifest.json`, then reads and hashes every file it lists. A missing file, a size or a sha256 that differs from the manifest stops startup with an error naming the file. A failed start never passes the rollout's health check. .dev and production each run one machine, which a rolling deploy replaces in place, so the game is down until the previous image is rolled out again.
- Text files (JS, CSS, HTML, JSON, SVG, about 3.5 MB) stay in memory after the check. Images and audio are read from disk on each request, so resident memory does not grow by 950 MB on the 2 GB machines. Those reads check the size against the manifest. An assets directory is never changed in place once verified; a new release is a new directory.
- In the source-tree case, node has just hashed the files, so the server does not hash them again.

### Exact-bytes replay for frozen rules bundles

A journal row names `full-card-world/N`. N must resolve to the bytes released as N, on every later server.

- `card_shared/rules.json` maps each version to the sha256 of its bundle: `{"133": "…", …, "204": "…"}`. A mint writes the bundle and appends one line. That file is the table the server runs from: the current version is the highest key, historical versions are the rest, and the upgrade order is numeric. It replaces the constants and match arms in `engine.rs` and `full_world.rs`, the output path hard-coded in `build-card-shared-engine.mjs`, and the 71 pins in `test/card-released-rules.test.mjs`, the four files every mint edits today.
- At startup every pinned bundle must appear in the manifest with exactly its pinned hash. A bundle's bytes are hashed again when it is first loaded for a replay. A mismatch refuses startup, and in the lazy case the version reports itself unsupported instead of running different bytes.
- The pins only grow. `test/card-released-rules.test.mjs` compares `rules.json` with the released base (`released-bundles.mjs`): a released version's pin may never change or disappear above the floor.
- Phase 4 (rules identity by content hash, stored in the database before any journal row names it) builds on the same pins and the same load path.

### Image

- Build stage: Rust only. It no longer needs `card-game/`, `v2/content` or Node, and `build.rs` watches only the C kernel.
- A new `assets` stage on the same `node:24` image the build stage borrows today copies the asset sources and runs `build-card-assets.mjs --release /out`.
- Runtime: `COPY --link --from=assets /out/media/ /app/assets/` (950 MB, changes only with art or music), then `/out/text/` (about 45 MB with the bundles), then the binary. Each is its own layer. A JS change leaves the media layer and the binary unchanged.
- The media layer is reused across runs only if the builder has a cache for it or the layer is reproducible. The main-push path builds on a fresh buildx builder and does not export a cache, so it also needs `SOURCE_DATE_EPOCH` and `rewrite-timestamp=true` in `scripts/build-release-image.sh`, or a registry cache for the `assets` stage. That is a workflow change; this design does not make it.

### Sync and reload on .dev (a later step)

- Keep releases on the volume: `/data/releases/<sha>/` holds the `text` tree (and `media` when art changed, hard-linked from the previous release otherwise). `COSYWORLD_ASSETS_DIR=/data/releases/current`.
- A non-Rust main push (classified by `scripts/check-deployment-impact.mjs`) builds the release directory, syncs it to the machine over Fly's private network, writes `manifest.json` last, and points `current` at it.
- The server then restarts in place (0.7 s cold start plus journal load), verifying the new directory before it serves. A failed verification exits, and a supervisor puts `current` back and restarts on the previous release. Hot reload without a restart can come later for public files only; rules and content changes go through a restart so that open shared worlds upgrade through the existing load path.
- A Rust change still builds an image. The binary layer becomes tens of MB instead of ~1 GB.

### What stays embedded

Nothing from `card-game/` or the generated outputs. There is no fallback copy: a fallback would serve bytes the manifest did not vouch for, and a server without its assets should not start. Rust-owned data (the C kernel, `card_policy`) and test fixtures behind `#[cfg(test)]` stay as they are.

### Order of work

1. Public files load from disk, served by the existing static handler; the image copies them; `build.rs` stops generating the asset module and stops watching `card-game/`.
2. Rules bundles load from `card_shared/` through `rules.json`, with the hash checks above.
3. `content.json`, `narrator.js`, `authored-text.json` and the JSON catalogs load from the assets dir.
4. The build stage and the image scripts drop Node and `card-game/`. A check proves that touching every file under `card-game/`, `v2/content/` and the generated outputs leaves `cargo build` fresh.
