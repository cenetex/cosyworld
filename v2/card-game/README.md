# Card world text and memory

Every avatar, item, and location has a profile in `entity-profiles.json` and a saved memory in the browser world. A memory holds the latest 16 witnessed events and the latest generated text. Card plays record events for the actors and objects present, the item used, and both places during travel. Generated speech and descriptions are marked as expressions, so the next prompt can distinguish them from game events.

After a card play, the browser sends the current local entities and departing avatars, their facts, avatar target hands, and eight recent memories, witnessed events, and the four latest spoken lines to `POST /card-game/text`. The Rust service adds the shared profiles and calls the configured world-content model through the existing AI gateway. One request covers the scene. It requests JSON-object output and validates one entry for each local entity. It returns one text for each local entity. Raising a card shows that entity's latest text. The place, played item, and chosen speakers also receive scene beats. Vale speaks first, followed by the chosen partner and witnessed arrivals or departures. A departing avatar says where they are going and why; their recorded farewell belongs to the source scene. The prompt includes the completed card play so their lines form a question and answer or a shared reaction. A separate resolved-turn record gives the played verb and outcome, every avatar's final location and holdings, exact travel companions, and final item ownership. Accepted accompany plays record both travellers; independent trips record an empty companion list. Current results take priority over desires and remembered speech. A wait play keeps Vale's words at the place where Vale stayed, and a solo farewell frames desired company as a hope for later.

The conversation shows generated text, with the prior spoken line and speaker portrait above the current line. The browser buffers each exchange until it passes validation, then reveals complete letters on a local clock with short pauses at punctuation. Vale speaks first. Each exchange advances after a reading pause. Tap the text to finish a line, then tap again to hear the next speaker. The hand cools down during generation and playback, then becomes ready after the last reply. A blinking cursor marks the end. Earlier lines and card memories can be replayed. Each speaker has a soft, pitched voice sound; the menu toggles it. Reduced motion shows full lines at once. Hidden tabs and open menus pause playback, including the rest of a punctuation pause. Text reveals on browser paint frames. The dialogue reserves space for both lines, and portraits stay mounted when the speaker changes. A card play holds the current spoken line while the next exchange is written. The browser saves complete text before playback begins. Fresh tables request an opening exchange. Reloading a turn whose words are still pending requests that turn again. Action records remain in the saved world and scene export.

The card rules still commit movement, trades, quest progress and inventory. The text response updates memories and scene lines. Revision checks discard old replies. Each play finishes its exchange before the next card action. Selecting a card then reads its memory. Completed lines return in full when switching back from an inspected card. Departure captions use the existing speaker heading, and the cutout fades after the farewell. A failed request leaves cards playable; the next play tries again. A new game or a save update from another tab cancels the old request.

Schema 4 saves include entity memories. Schemas 1 through 3 migrate using their recorded history. Scene exports include entity memories and generated beats.

## Local play

Run the Rust server with `COSYWORLD_PRIMARY_GAME=cards` and the normal AI provider configuration. It serves both the game and the text route. For the lightweight card server, set `COSYWORLD_CARD_TEXT_ORIGIN` to the Rust server's origin before running `npm run play:cards`. Provider credentials stay in the Rust service. `COSYWORLD_CARD_TEXT_MODEL` selects a registered world-content model for this card table. Both production sites use `openai/gpt-6-luna` with `COSYWORLD_CARD_TEXT_REASONING_EFFORT=none` for short scene text.

The endpoint accepts at most 64 KiB, fixed entity IDs, eight local entities, and bounded facts and memories. It allows two model requests at once, 30 requests per peer per minute, and 1,200 requests per process per hour. Same-site browser requests pass the origin check. Model calls have a 25-second deadline. Clients send `Accept: text/event-stream` for live text deltas followed by a validated `complete` event with all entries and the resolved model name. Other clients receive the full JSON response. Disconnects cancel the provider request and release its capacity.


## Threats and standoffs

Avatar cards offer Talk and Threaten. A threat opens a standoff between the two avatars and adds Guard and Attack to their cards. Each has four resolve. An attack removes two resolve between equal levels, three against a lower level, and one against a higher level. Guard softens the next hit by one, with a minimum of one damage, until that avatar's next play.

Talk and item trades stay available during a standoff. Travel ends it; releasing the disputed item settles it. At zero resolve, the losing avatar drops the disputed item (or an item the winner needs) and retreats along a normal path. Both avatars get three turns to recover before another threat. Quest programs still award levels.

The cast starts with a guard or a brave reply. It responds to attacks, and a challenger can press an item demand after two turns. In generated quest programs, two refused requests for an item both avatars need can lead to a threat. Every threat, guard, hit, release and retreat enters the witnesses' memories. Saves from earlier versions gain an empty standoff state.

## Accompany requests

Pair a nearby avatar with an open location card to ask them to accompany Vale. Either card order works. Tap either raised card, or drag the pair into the scene, to play the request. Pairing Vale with a location travels there directly.

The invited avatar chooses from the alternatives in its current target hand. It first seeks any wanted item left here, then travels toward distant items, its target location, or wanted company. Items carried by Vale travel with the request, so an avatar can join its supplier. An avatar attends to an active standoff or recovery before accepting a trip.

The request and reply take one round. An agreement moves both avatars together, with their own items and attached covers. Each avatar uses its normal travel action; fuel and ringing advance once. The other cast member takes its normal turn. Each avatar resumes its own goals on the next play. Hands fulfilled during the joint arrival count toward both quest programs.

Requests record the destination and the answer in the scene script. Both places, witnesses, avatars and carried items remember an agreed trip. The same model request writes Vale's invitation and the invited avatar's reply from the completed result, desires, personas and memories.
